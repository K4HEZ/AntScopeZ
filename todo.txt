5) Busy indicator (the red dot PopUpIndicator draws at m_swrWidget's own
   upper-left corner, see popupindicator.cpp) -- reported 2026-09-05 as
   "only lights up during the last portion of the scanning/plotting
   activity".
   -- First pass misdiagnosed this: grepped PopUpIndicator call sites in
      src/*.cpp only, missed analyzer/analyzerpro.cpp entirely, and
      concluded (wrongly) that it was calibration-only. It's actually
      shown/hidden around every ordinary scan too (on_measure()/
      on_measureS21()/on_measureContinuous()/on_measureUser(), analyzer/
      analyzerpro.cpp) -- the Short/Load calibration asymmetry fix above
      still stands on its own merits, just wasn't the reported bug.
   -- Corrected diagnosis, from the user's own precise repro (a 400-point
      SWR scan, indicator dark for points 0-255, lit for 256-400): traced
      to NanovnaV2Analyzer::requestFifoChunk() (nanovna_v2_analyzer.cpp)
      -- the V2/LiteVNA64 binary protocol's READFIFO count is a single
      byte on the wire, so a >255-point sweep is always fetched as 2+
      chunks (255, then the remainder) entirely internally -- AnalyzerPro
      and its stitching (g_analyzerMaxPoints) never see this at all, it's
      a lower tier. Root cause: PopUpIndicator::showIndicator()'s
      QWidget::show() only *posts* a show/paint event; the window isn't
      actually mapped/painted until the event loop next spins.
      processFifoChunk()'s per-point emitPoint() calls run in a tight
      synchronous loop (up to 255 back-to-back on_newData()/chart-replot
      cycles) with no gap for the event loop to catch up until the
      request boundary between chunks -- which is exactly the idle gap
      (waiting on the next chunk's bytes over the wire) that finally let
      the window get its first paint.
   -- processEvents() fix (above) confirmed NOT sufficient -- user
      retested live (real hardware, wire-level READFIFO log alongside):
      still dark for the whole first 255-point chunk, only appears once
      the second (146-point) chunk starts. Whatever's actually happening
      isn't just "the window's first paint got delayed a few ms" --
      re-audited every PopUpIndicator call site again from scratch and
      found one more that earlier passes missed both times:
      AnalyzerPro::setIsMeasuring() itself unconditionally calls
      PopUpIndicator::setIndicatorVisible(_isMeasuring) (line ~981) --
      redundant with on_measure()'s own explicit show call a few lines
      later (both fire "true" once, at the very start), and every
      "false" call is one of the same already-audited completion/stop
      paths. Doesn't explain the timing on its own either.
   -- Genuinely stuck without live data -- statically, every show(true)
      call happens once, right at scan start (before any wire I/O for
      the first chunk even goes out, since NanovnaV2Analyzer::
      sendCommandBytes() is a plain async QSerialPort::write(), not
      blocking), and every hide(false) call is gated to true completion
      or an explicit stop/interrupt. Nothing in the code should be able
      to produce "dark for chunk 1, lit for chunk 2". Rather than a
      3rd blind guess, added TEMPORARY qDebug() instrumentation (tagged
      "[BUSY]", timestamped hh:mm:ss.zzz to line up against the wire-
      level chunk log) at every show/hide call and at NanovnaV2Analyzer's
      requestFifoChunk()/processFifoChunk() chunk boundaries
      (popupindicator.cpp, analyzerpro.cpp's setIsMeasuring(),
      nanovna_v2_analyzer.cpp) -- run from a terminal so qDebug output is
      visible, reproduce the same scan, and the interleaved timestamps
      should show exactly which call (if any) is missing/out of order.
      Remove all of it once this is actually root-caused.
   -- Root-caused 2026-09-05 from that live [BUSY] log (real hardware +
      dev emulator, run from a terminal): showIndicator() genuinely ran
      at scan start, and isVisible() was already true well before chunk
      1 began -- Qt's own bookkeeping was correct the whole time. What
      the log actually revealed: processFifoChunk() costs ~20ms/point,
      confirmed from its own start/done timestamps (255 points -> 5.05s;
      146 points -> 2.85s, both ~20ms/point) -- one single synchronous
      call per chunk, no event-loop turn between points (each point's
      emitPoint() triggers a full chart replot inline). QApplication::
      processEvents() (the first fix) only dispatches whatever's already
      queued in Qt's own event queue -- it doesn't wait for a round trip
      to the X11/Wayland compositor, and that round trip's result never
      arrived before the ~5s freeze began, starving the indicator's
      first-ever paint for the freeze's *entire* duration. It only
      actually got painted for the first time in the brief gap between
      chunks -- and, like any window whose owning process has stopped
      pumping the event loop, kept showing that one frame right through
      the second chunk's own ~2.85s freeze, which is what made it look
      like it "started working" exactly at the chunk boundary.
   -- Fixed: showIndicator() now also calls QGuiApplication::sync()
      after processEvents() -- the documented way to force that round
      trip to actually complete before returning, so the first paint can
      no longer land inside a freeze regardless of how long one
      particular chunk's synchronous burst turns out to be. [BUSY]
      logging kept in place (now also logs isVisible() post-sync()) for
      one more live confirmation pass; remove once confirmed.
   -- Separate finding, deliberately NOT touching the per-point replot()
      cost itself: Harold wants to keep every point drawn live as it
      arrives, even at ~20ms/point. Instead, made Stop responsive without
      changing that: NanovnaV2Analyzer::processFifoChunk()'s per-point
      loop (and NanovnaAnalyzer::parseBinaryScan()'s equivalent, classic-
      protocol binary-scan loop -- same pattern, and its m_binaryPoints
      can be the *entire* scan in one reply, e.g. all 10000 points, not
      capped at 255 like V2's wire-level FIFO count, so it was arguably
      the worse offender for "can't cancel a big scan") now call
      QCoreApplication::processEvents(QEventLoop::ExcludeSocketNotifiers)
      once per point and `break` if isMeasuring() has gone false. No new
      "abandon the rest" logic needed: AnalyzerPro::on_newData()'s
      existing stale-data-after-stop guard already turns every further
      emitPoint() in the same burst into a cheap no-op (no replot) the
      moment the Stop click's handler runs mid-loop and flips
      isMeasuring() -- break just skips the now-pointless remaining
      per-point math on top of that. NanovnaV2Analyzer::
      processFifoChunk() additionally skips requesting the *next* FIFO
      chunk once stopped (nothing to actually drain either way -- a
      chunk not yet requested has nothing in flight on the wire to wait
      out). ExcludeSocketNotifiers: lets the Stop click (an ordinary UI
      event) through while keeping a hypothetical early/unsolicited
      readyRead() for the same port from reentering mid-parse. Not yet
      confirmed live -- the "unable to cancel a 10000-point scan" repro
      that prompted this needs a real retest.
   -- REVERTED 2026-09-05, same day: broke real hardware badly -- "scan
      won't start... multiple attempts to reconnect to get it working,
      stopping a scan doesn't drain." Both loops (NanovnaV2Analyzer::
      processFifoChunk(), NanovnaAnalyzer::parseBinaryScan()) are back to
      exactly what they were before this attempt -- no
      QCoreApplication::processEvents()/isMeasuring()-check/break, no
      QCoreApplication include, in either file. Root cause of the
      regression not yet diagnosed -- the ExcludeSocketNotifiers
      reasoning (blocks readyRead() from reentering) is the prime suspect
      for "won't start"/"needs reconnects": *something* in the connect/
      handshake or drain path may depend on socket-notifier events firing
      during what looks like an ordinary processEvents() pump elsewhere,
      or reentering processFifoChunk()/parseBinaryScan() itself (already
      mid-parse of one chunk) via a nested readyRead() might not be as
      safe as assumed if events *other* than sockets still let unrelated
      code run that touches the same parse state. Needs a real
      root-cause pass before trying again, not just a retry -- the busy-
      indicator sync() fix and [BUSY] debug logging (separate files,
      untouched by this revert) are still in place and still awaiting
      their own live confirmation.
